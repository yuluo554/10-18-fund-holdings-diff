> **目标产出**：`10-18-fund-holdings-diff`（`10-18` 为仓库编号标签，沿用本系列目录命名；**题面定稿日期 2026-10-17**；GitHub 仓库名沿用 `10-18-fund-holdings-diff`）。
> **交付形态**：**纯本地 Python CLI + 本地季报报告（Markdown + 单文件 HTML）**（无服务器、无 GPU、无账号体系、无数据上传）。
> **题目定稿日期**：2026-10-17　**题目版本**：v1（首版定稿）　**查证基准日**：2026-10-17
>
> **定位宣言**：维护自选基金清单 → 抓季报前十大持仓 → 与上季做 diff（新进/退出/加仓/减仓）→ 叠加基金经理变更与规模变动 → 生成"这一季我的基金换了什么"的本地报告。**不是实时估值工具，是季度事件回顾**。竞品停在"爬取/汇总"层，没人把"季度 diff + 经理变更 + 规模变化"合成一份可读季报。

## 一、项目介绍

### 1.1 痛点

一个人手上通常有 5–20 只自选基金，分散在主动权益、指数增强、行业主题里。季报发布后，真实的问题不是"今天涨了多少"，而是三件事：**这只基金这一季换了哪些重仓股？基金经理换人了吗？规模是暴增还是被赎回？** 这三个问题在基金销售平台上分别散落在三个页面，且平台只展示"当前季"的前十大，不给你跟上季并排看；也没有任何一家平台告诉你"你自选的那 12 只基金，这一季合计新进了哪些股票"。

持有人真正想做的是**季度复盘**：一年四次，每次花二十分钟，把清单里每只基金的季报变动看一遍。这件事目前只能手工做——打开 N 个页面，抄两次前十大，自己拿眼睛比。

**差异化只能押在这四处**：

1. **Q/Q diff 状态机**——不是"展示本季前十大"，而是把两季持仓对齐成 `新进 / 退出 / 加仓 / 减仓 / 不变` 五种状态的确定性判定，且判定规则**一处定义、可配置、可回放**；
2. **经理变更叠加**——把"本季内是否发生经理变更"与"变更日期落在报告期内哪一天"叠加到持仓 diff 上，回答"人换了，仓位跟着变了吗"；
3. **规模变动**——申购 / 赎回 / 份额 / 净资产四条曲线并排，区分"净值涨出来的规模"与"申赎带来的规模"；
4. **可审计的变动台账**——每一条变动都能溯源到两个季度的原始字段（哪个接口、哪个字段、原始值是什么），而不是一句"新进"。

### 1.4 数据源与结构性限制（这是本题最重要的部分，不粉饰）

**先说限制，再说方案。** 本题有三个无法用工程手段消除的结构性限制：

**限制①：季报是低频数据。** 公募基金季报按季度披露，Q3 报告期截止 **9/30**，披露截止 **10 月底**——一年只有 **4 次**新数据。工具在一年中的绝大部分时间里**没有新数据可处理**。这意味着：本题的验证不能依赖"实时新鲜度"，必须靠**历史季度回放**与**合成数据**；产品形态必须是"事件驱动的手动触发"，不能做成常驻服务；"每天打开都有新内容"的预期在这题里是错的，必须在 README 第一屏讲清楚。

**限制②：东财接口的 ToS 边界。** 东方财富的公开页面/接口，其服务条款通常**禁止批量抓取与再分发**。本题的处理是硬约束而非建议：**仅个人本地低频使用、不建公开镜像、不再分发原始数据、不将抓取结果入库发布**。任何"把全市场持仓数据打包成数据集发 GitHub"的做法都超出本题边界（见 §六）。这条限制直接决定了"全市场反向穿透"只能作为扩展项，且必须在本地运行、结果不随仓库分发。

**限制③：巨潮基金栏目收录滞后（实测）。** 巨潮资讯的基金栏目（`column=fund&category=category_jdbg_jjgg`）在 **2026-10-01 ~ 2026-10-17** 区间返回 **0 条**，而同期 Q2 窗口有 **1023 条**。也就是说：在证监会已发布 Q3 报告元数据的情况下，巨潮的类别检索仍是空的。**巨潮不能作主源**，只能作为备用核对渠道。

**数据源策略（首期定案）**：**证监会 eid 作"报告已发布"的权威信号（只取元数据）→ 东财补字段（持仓 / 规模 / 经理）→ 两者交叉校验**。判定顺序不可颠倒：先问"这份季报发了没有"（官方元数据），再问"里面写了什么"（商业接口字段）。东财仅个人本地低频使用、不建公开镜像、不再分发原始数据。

### 1.5 为什么是工具而不是让 AI 聊天算（独特性拷问）

季报变动是**跨期状态比较**：要稳定保存"上季十只股票 + 各自占比"，才能在下一季做对齐；要保证同一份季报两次跑出同一份 diff；要把"接口给的变动方向"与"自己算的占比差"对不上时明确报冲突而不是含糊过去。聊天式交互没有可审计的持久台账，也无法在不同时间点用同一规则复算历史。**diff 的判定规则必须冻结、可配置、可回放**，这是工具才具备的性质。

## 二、任务要求

> **首期范围限定为五个模块（M1–M5）**。全市场反向穿透、更多份额类别、历史多季趋势为扩展项（见本节末）。
>
> **数值口径一律以 `data/README.md §四` 为唯一来源**（变动判定规则、季报窗口定义、限频与退避、合规词表），本文出现的阈值均为引用，**不得手写第二份口径**。

### M1 基金清单与季报窗口

- **输入**：用户在本地的自选基金清单（增删改查）；`fundcode_search.js` 缓存。
- **输出**：清单存储（本地 SQLite 或 JSON，二选一后冻结）、`code → 名称 / 类型` 映射、**"本期报告窗口"标识**、逐基金的**披露状态**（`已披露 / 待披露 / 无数据`）。
- **确定性纪律**：
  - 清单操作**只写本地**，不产生任何网络请求；代码→名称映射**按需缓存**，缓存未命中才拉取，拉取失败不影响已缓存条目；
  - **报告窗口的定义写死在配置**（如"报告期截止日 + 披露截止日"），不从当前时间反推；`--as-of` 参数可把工具固定在某个历史日期上复跑，**不读系统时钟做隐式判断**；
  - 披露状态以**证监会 eid 元数据**为准：eid 中能找到对应报告期即 `已披露`，找不到即 `待披露`；网络失败落 `无数据`，**三者严格区分，不合并成"没有"**；
  - **未披露基金必须标"待披露"并正常退出**，不得报错、不得跳过而不留痕。
- **验收**：清单增删改查幂等（重复添加不产生重复条目）；对一批混合状态的基金代码运行，`待披露` 与 `无数据` 分别可见；`--as-of` 指向历史日期时，状态与当日快照一致。

### M2 持仓抓取与归一

- **输入**：M1 的清单与披露状态。
- **输出**：**归一持仓台账**（每行：基金代码 / 报告期 / 股票代码 / 股票名称 / 占净值比 / 变动类型 / 变动百分点 / 所属行业 / 原始来源 / 抓取时间戳），以及**逐基金抓取状态台账**（成功 / 空持仓 / 失败原因）。
- **确定性纪律**：
  - **双通道**：优先走 `FundMNInverstPosition`（JSON，直接给增持/减持与变动百分点）；缺失或字段不全时回落 `jjcc` 页面解析（GBK 解码 + 内嵌 JS 正则提取 `var apidata={content:"…"}`）；**回落必须记录在台账里**，报告可见"本条来自页面解析"；
  - **编码显式声明**：`jjcc` 一律按 GBK 解码，解码失败即报错并保留原始字节快照，**不做 `errors="ignore"` 式的静默丢字符**；
  - **字段归一**：占净值比统一存为数值（去掉 `%`），变动百分点保留符号；行业字段缺失时落 `null` 而非空串；股票名称做全角/半角与空白清洗，但**不修改字符本身**；
  - **失败隔离**：单只基金失败不影响其他基金；重试采用**指数退避 + 上限次数**，退避参数在配置中一处定义；最终失败落 `失败原因` 并计入报告首页计数；
  - **ETF 联接 / QDII / LOF 的表格差异必须显式标注**（如联接基金可能无股票持仓、QDII 行业字段缺失），**标注为"结构差异"而不是"解析失败"**。
- **验收**：对已披露基金跑通"JSON 通道"与"页面回落通道"各一遍，两者在同一基金上的股票代码集合一致（占比允许按口径差异说明）；构造一个无股票持仓的联接基金，输出为空持仓且不报错；构造一个网络失败用例，其他基金结果不受影响且失败台账可读。

### M3 Q/Q diff 引擎（核心）

- **输入**：M2 的两季持仓台账（本期 + 上期）。
- **输出**：**变动台账**（每条：基金代码 / 股票代码 / 名称 / 上季占比 / 本季占比 / 状态 / 变动百分点 / 判定依据 / 两条原始记录的溯源指针），以及按基金的**变动摘要**（新进 N、退出 N、加仓 N、减仓 N、不变 N）。
- **确定性纪律**：
  - **变动判定规则一处定义**，且必须**二选一并写进配置**（不允许"两个都用、看哪个合适"）：
    - **方案 A（机构口径）**：直接采用接口给出的 `PCTNVCHGTYPE`（增持 / 减持 / 不变）与 `PCTNVCHG`；
    - **方案 B（自算口径）**：以两季占净值比之差判定，`|Δ| < 阈值` 判 `不变`，否则按符号判 `加仓 / 减仓`；阈值在 `data/README.md §四` 定义一次。
    - 配置项 `diff.mode = "provider" | "computed"`，**报告页眉必须标注本次所用口径**。
  - **状态机是闭合的五态**：`新进 / 退出 / 加仓 / 减仓 / 不变`。上季有本季无 = `退出`；上季无本季有 = `新进`；两季都有且判定为增/减/不变；**不允许出现第六种状态或 `unknown` 静默通过**——无法判定的记录进"待确认"并在报告中计数；
  - **冲突可见**：当方案 A 的机构口径与方案 B 的自算口径方向相反时，报告必须列出"口径冲突"清单（这是数据质量的信号，不是可以平均掉的噪声）；
  - **每条变动可溯源**：台账中每条记录携带**两条原始记录指针**（上季与本季各自的来源、报告期、原始字段值），报告可下钻；
  - **排序与输出确定性**：按基金代码、再按本季占比降序（同占比按股票代码升序）固定排序；同一输入两次运行输出**字节一致**。
- **验收**：合成真值中植入的五类变动（新进 / 退出 / 加仓 / 减仓 / 不变）逐条对齐；方案 A / B 各跑一遍，冲突清单可解释；同一输入双跑 diff 结果字节一致。

### M4 经理变更与规模变动

- **输入**：M1 清单；M2/M3 的报告期。
- **输出**：**经理变更台账**（基金经理姓名 / 任职起止 / 变更日期 / 是否落在本报告期内 / 来源）、**规模变动台账**（报告期 / 期间申购 / 期间赎回 / 期末份额 / 期末净资产 / 份额变动率）。
- **确定性纪律**：
  - **经理变更解析**：从 `jjjl` 页面解析"基金经理变动一览"（变更区间、经理姓名、天数、任期回报）与"现任基金经理简介"（上任日期）；页面为 UTF-8；**解析失败落"未解析"并保留页面快照，不猜测**；
  - **"本季内变更"的判定**：变更日期落在 `[报告期起始, 报告期截止]` 内才标注为本季内变更；跨期变更标注"上季末已变更"；**判定区间来自配置，不来自当前日期**；
  - **规模四条口径不混算**：申购、赎回、份额、净资产**分别入台账**；"份额变动率"若接口直接给出则引用并标注来源，若需自算则公式在 `data/README.md §四` 定义，**禁止把两个口径的数字相减当结论**；
  - **缺失处理**：新成立基金无上季数据时，规模变动落 `无上季基准` 而非 `0`；**0 与缺失必须区分**；
  - **合规红线**：经理姓名只作为**变更事件的主体标识**，**不得**据此做能力评价、排名、推荐或业绩归因。
- **验收**：构造"本季内变更""上季末已变更""无变更"三类样本，标注正确；规模变动中缺失与 0 可区分；报告静态扫描不出现能力评价类表述（见 M5 合规门禁）。

### M5 本地季报与合规门禁

- **输入**：M1–M4 的全部台账。
- **输出**：**`report.md` + `report.html`（单文件，零外链）+ `report_data.json`（与 HTML 同源）**。报告按基金分组，每组含：变动摘要 / 变动明细 / 经理变更 / 规模变化 / 数据来源标注；报告间可**与上期报告对比**（新增基金、本期无变动的基金、累计变动）。
- **确定性纪律**：
  - **单文件 HTML**：零 CDN、零外链、零网络请求、零遥测；断网可生成；
  - **页脚固定合规文案**：`非投资建议` + `来源：基金季度报告`，**位置与文字冻结在模板里，不可通过配置关闭**；
  - **合规词表检查（硬门禁）**：报告中不得出现 `抄作业` / `跟随基金经理` / `推荐` / `买入` / `抄底` / `必涨` 等表述；词表在 `data/README.md §四` 一处定义；生成后**扫描 HTML 与 Markdown 正文**，命中即**非零退出**并列出命中位置；
  - **口径页眉**：报告页眉必须标注本次 diff 口径（provider / computed）、报告窗口、数据基准日、抓取时间戳；
  - **数据来源逐条标注**：持仓标 `来源：基金季度报告`；规模与经理标 `来源：基金定期报告公开披露`；**不把商业接口写成官方来源**；
  - **不出现个性化投资结论**：只陈述"发生了什么"，不写"因此应该……"。
- **验收**：断网生成全流程退出码 0；HTML 静态扫描 0 外部资源引用；合规词表注入一条违规文本时**必须非零退出**且定位到具体行；同一输入两次生成报告字节一致。

### 扩展项（首期不做，不承诺交付）

- **全市场"某股票被哪些基金持有"反向穿透**：需求真实（见 §一 V2EX 2020-07-04 与 MoneyRush #46），但**受 ToS 限制**——只能本地运行、结果不分发、不建公开数据集；且全市场抓取量与限频边界需要单独评估，首期不承诺。
- **更多份额类别**（A/C/E 类份额的逐类对比）：份额类别与持仓基本一致但规模不同，价值在规模对比，首期只做清单中显式登记的代码。
- **历史多季趋势**（>2 季）：需要更长的历史回放与存储设计，首期只做相邻两季。

## 六、边界与非目标

- **非投资建议（最重红线）**：**不推荐、不排名、不预测收益、不给买卖信号、不做择时评价、不做基金经理能力评价**。所有输出是"已经披露的季报里发生了什么"的事实回顾，**不构成任何投资建议**。报告中禁止出现"抄作业 / 跟随基金经理 / 推荐 / 买入"类表述，并由合规词表**硬门禁**兜底。
- **不做实时估值 / 盘中净值**：本题不是估值工具。与主流"实时估值"需求**主动切割**（见 §1.2 反证），不接盘中行情、不算当日估算净值。
- **不做基金筛选推荐**：不提供"哪只基金更好""该买哪只"的排序或打分；不构建基金评价体系。
- **不做全市场公开镜像与数据再分发（ToS 边界）**：东财接口仅个人本地低频使用；**不建公开数据集、不把抓取结果打包发布、不在仓库内提交真实抓取的全量数据**。仓库内的样例一律为**合成快照**。全市场反向穿透只作为本地扩展项，且结果不随仓库分发。
- **不绕验证码 / 不绕登录 / 不绕反爬**：遇到验证码、登录墙、频控即**停止并落台账**，不做任何规避。限频与指数退避参数在 `data/README.md §四` 一处定义。
- **不承诺覆盖全部基金类型**：首期以**股票型 / 混合型**为主；ETF 联接 / QDII / LOF **只标注结构差异，不承诺字段完整**；货币基金、债券基金的首十大口径不同，首期不承诺。
- **必须写进 README 第一屏的结构性限制**：**季报一年仅 4 次更新，工具大部分时间没有新数据**。这不是缺陷，是产品定位——它是季度事件回顾工具，不是常驻服务。
- **隐私红线**：自选基金清单**纯本地存储**，不上传、不同步、不做账号体系；报告中的清单与持仓**不携带任何个人身份信息**（本工具不采集用户身份）。
- **品牌隔离**：本题只做**公募基金定期报告**，不涉及上市公司公告、不涉及证券交易流水、不涉及任何其他项目领域；文档不提及任何其他项目。
- **首期范围限定**：M1–M5 进首期 DoD；**全市场反向穿透、更多份额类别、历史多季趋势一律为扩展项**，不在首期承诺交付。
- **免责**：季报数据版权属基金公司，引用注明"来源：基金季度报告"；经理变更属公开信息，仅作事件记录；**数据与官方披露存在差异时以基金公司公告及证监会披露为准**。
